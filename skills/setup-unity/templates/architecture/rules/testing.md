# テスト・検証方針

## 大原則

**書きすぎない。** AI はテストを量産しがちで、低価値テストは保守コストだけ増やす。
「このテストだけが殺せる回帰」を 1 文で言えないテストは追加しない。

実装後に何を回すか（PR 前チェック・動作確認・完了報告）は `rules/dev-flow.md` が正本。

## テスト層

自動テストは **EditMode の単体 / ロジックテストに限定**する。

- 検証するのは「メソッドの直接呼び出しで起動する振る舞い」（純ロジック・状態遷移・エラー変換等）
- PlayMode / 統合テスト / 視覚検証は自動スイートで扱わない（`rules/dev-flow.md`「ランタイム動作確認」へ委譲）
- 選別は **Unity ランタイム依存の有無**で決める。MonoBehaviour に純ロジックが埋まっているなら、
  テストをこじ開けるのでなく plain class への分離を提案する

## テスト責任

Claude は明示されなくても、変更差分ごとにテスト要否を判断する。
**判定は層名ではなく「plain class か、Unity ランタイムに依存するか」で行う**（Presentation のクラスでも plain class なら対象）。

原則としてテストを追加または更新する:
- Domain / Application / Shared のロジック変更
- **Presentation の plain class**（Model / Manager / Provider 等）の値域制約・導出・状態遷移・
  入力正規化・Clear 処理
- UseCase の状態更新、rollback / fallback、呼び出し順序、キャンセル伝播
- **固有の**エラー変換・状態巻き戻し・副作用を持つ失敗分岐
- Infrastructure の外部由来の入力の解釈（DTO 変換、URL / path / header 組み立て、
  レスポンス解釈、**外部由来**のエラーコード変換、認証情報の扱い）

テスト不要と判断してよい:
- Presentation の見た目・配置・Inspector 配線を含む変更
- View / Binder / Presenter の変更（Presenter に配線以上のロジックが入ったら、テストではなく
  Model への切り出しで対応する）
- コメント、XML summary、typo、ドキュメント
- enum / DTO / record / struct の項目追加と、その素通しのマッピング追加
- 単一依存の失敗をそのまま転送する経路、転送のみの facade / パススルー
- context 境界をまたぐ内部 enum の再マッピング（外部由来の入力を注入する経路ではない）
- 既存テストが変更後の仕様をカバーしている変更
- Unity ランタイム・SDK・外部サービス・実機操作に依存し、手動確認のほうが適切な変更

**両方に該当するなら「追加前ゲート」を優先する。** 例: DTO に項目を 1 つ足して 1 対 1 で
マッピングする変更は「DTO 変換」に見えるが、書けるテストの実体は代入確認なので追加しない。

依存の失敗パスを検証するかは、その依存の**出自**で決める。

| 依存の出自 | 判断 |
|:--|:--|
| 外部ライブラリ / framework / SDK / backend（所有外） | **テストする。** stub でエラーを注入し、変換・ガード・状態整合を見る |
| 自前コード（別レイヤー・別 context のコンポーネント） | **skip。** その依存の単体テスト側が守る |
| 不明 | `AskUserQuestion` で確認する。確認できないならテストせず報告する |

エラー変換の検証は「変換の方針」に絞る（未知コードが既定値へ落ちる / 情報を落とさない /
変換後も状態が整合する）。代表 2〜3 件で足りる。enum の 1 対 1 対応表を第 2 の場所へ写経しない
（表を間違えたまま両方直せば黙って通るので、回帰を殺さない）。

## 追加前ゲート

追加候補ごとに **4 つすべて**満たすか確認する。1 つでも欠けたら追加しない。

1. **回帰特定** — そのテストが落ちる具体的な実装改変を 1 つ挙げられること（どのメソッドの
   どの条件式・どの代入をどう変えると落ちるか）。「仕様を守る」「正しく動く」は説明ではない
2. **一意性** — ゲート 1 で挙げた改変が既存テストも落とすなら、字面が違っても重複。
   同一ガードを公開 API の数だけ反復しない（残すのは最上位の入口 1 件）。入力値だけが違う
   再確認はパラメータ化で集約する。同一 condition を multi-assert に統合しない（1 ケース 1 検証。
   例外は「状態遷移後に複数プロパティが同時に正しくある必要がある場合」と「初期契約」）
3. **仕様語 ↔ assertion 整合** — 意図に仕様語（順序 / rollback / fallback / エラー変換 /
   状態遷移 / キャンセル伝播）が出るなら、それを実際に観測する assertion があること。
   検証内容には**観測可能な性質だけ**を書く（rationale・テスト機構・入力の構築手順を混ぜない）
4. **ダブルの語彙** — 「呼ばれたか・順序」なら **spy**、「SUT を動かすため」なら **stub / fake**。
   stub は arrange の関心事なので検証意図に書かない

無効入力は出自で分ける。**UI から入りうる無効入力**は実在する失敗経路なのでテストする。
**仕様が挙動を定義していない無効入力**は推測して期待値を作らない — `AskUserQuestion` で確認し、
できなければ未定義仕様として報告してそのケースは書かない（現行実装の挙動を期待値にすると、
実装のスナップショットを固定するだけになる）。

## 書いた後に必ず通す（重複整理）

テストを書いた後、追加・変更したファイルと同一テストクラスの既存テストを読み直す。
この段が「AI がテストを書きすぎる」傾向への構造的な歯止め。

- **重複**（ゲート 2 の定義）→ より正確な名前のものを残し、他を削除
- **パラメータ化マージ** — condition が違っても「引数だけが違い、同一同値区分で同一の期待結果」なら
  1 メソッドへ統合する。本体に `if` / `switch` を書かない。**期待値をパラメータ化しない**
- 以下のみを検証する既存テストを見つけたら**削除を提案する**（追加時のフィルタだけでは蓄積し、
  しかも「既存テストで十分」判定の材料に化ける）:
  **スタブに仕込んだ値がそのまま返ることの確認**（SUT が転送しかしていない ＝ 恒等写像）/
  下位の単体テストで既出の結果 state を合成側で再検証するだけのもの /
  エラー enum の 1 対 1 対応表の写経 / 初期値だけの確認（下記の例外を除く）/
  仕様語を主張するが観測する assertion を持たないもの（fake assertion）/
  実装の分岐をなぞるだけで仕様を表していないもの

初期値テストの例外は、外部購読される状態の**初期契約**（購読側が初期値に依存して表示・分岐を
決める）を守る場合のみ。その場合もプロパティごとに分けず 1 メソッドへまとめて assert する。

## テスタビリティ

「テストが書きにくい」は、テストの問題ではなく**対象コードの設計問題**の兆候。
境界が引けない・状態が観測できない・組合せ爆発・依存が注入できない・MonoBehaviour に
純ロジックが埋まっている — このどれかならテストをこじ開けず、設計見直しを報告する
（`rules/coding-standards.md`「設計アプローチ」）。

## この環境の決めごと

配置と命名の一部は他が正本 — `Tests/EditMode/` 配置は `rules/folder-structure.md`、
テストクラス名は `rules/coding-standards.md`。ここへ書き写さない。

| 項目 | 決めごと |
|:--|:--|
| namespace | `<Project>.Tests.<Context>`（`<Project>` は既存テスト・asmdef 名で確認） |
| テストメソッド名 | `MethodName_Condition_ExpectedResult`。パラメータ化の `Condition` は個別引数でなく同値区分名 |
| UniTask の駆動 | `[Test] public void` + `.GetAwaiter().GetResult()`（stub は同期完了する）。実際に await が要る場合のみ `async Task`。`async void` は禁止。`[UnityTest]` は実フレーム経過が要る場合のみ |
| キャンセル | 実引数に `CancellationToken.None` を明示、検証時は `CancellationTokenSource`（プロダクト側の `ct = default` 回避方針とは別の話） |
| テストダブル | `Tests/EditMode/TestDoubles/<Context>/` に共有定義。同一 interface を private nested で重複定義しない。Moq 等の生成フレームワークは使わない |
| spy | 共有スタブに **opt-in の `CallLog`**（null なら記録しない）と結果上書きフィールドを持たせ、呼び出し順を観測する。結果上書き = stub、`CallLog` = spy |
| Result 型 | `IsSuccess` を見てから `Value` / `ErrorCode` を assert。開発者向け診断文言（`ErrorMessage` 等）は値を assert しない |
| 期待された警告 / エラーログ | `LogAssert.ignoreFailingMessages` を `try` / `finally` で挟んで抑止する |
| asmdef | **まず実ファイルを読み**、対象アセンブリが `references` にあるか確認して不足のみ追加する（既存設定を雛形で上書きしない） |
| `R3` | `ReactiveProperty` は購読時に現在値を流す（初期値テストの例外はこの性質による） |

## 実行スコープと罠

- **全件実行は CI**（`.github/workflows/unity-ci.yml` の test ジョブ）。ローカルは変更差分の
  スコープだけ回す（`unity test --mode EditMode --filter <名前空間>`）。同じ全件実行を 2 箇所で走らせない
- 外部アセット欠落等でプロジェクト外のテストが常に失敗する場合、workflow の `TEST_FILTER` に
  **残したい**名前空間を書く（`--filter` は選択であって除外ではない）。値の正本は workflow の
  1 箇所だけ。ここへ書き写さない
- **`--filter` は 0 件マッチでも exit 0 を返す。** 名前空間をリネームすると偽の緑になるので、
  ローカルでも CI でも実行件数を確認し、0 件なら緑と扱わない
- 不安定なテストを一覧で管理しない。`unity test --retries <n>` がリトライで通ったものを
  **flaky** として報告するので、その報告を根拠に対処する
