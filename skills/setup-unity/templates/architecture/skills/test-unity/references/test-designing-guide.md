# テスト設計ガイド（何をテストするか）

テストケースを「何を・どの粒度で検証するか」を決めるための判断基準。
**コードを書く前（または書き直す前）にこのガイドで設計し、実装規約は `test-writing-guide.md` に従う。**

大原則は 2 つ:

1. **テストは仕様（観測可能な振る舞い）を守る安全網である。** 実装をなぞる写経ではない。
2. **書きすぎない。** AI はテストを量産しがちで、低価値テストは保守コストだけ増やす。
   「このテストだけが殺せる回帰」を 1 文で言えないテストは追加しない。

---

## 1. テスト対象の選別

「原則テストする変更」「テスト不要と判断してよい変更」の一覧は `rules/testing.md`「テスト責任」を
単一ソースとする（呼び出し順序・キャンセル伝播などを含む）。ここでは重複させず、
テスト設計時に補足が要る観点だけを以下に挙げる。

### 選別は層名ではなく「Unity ランタイム依存の有無」で決める

層で切ると、テストしやすい plain class が層名だけで除外される。判定は型の性質で行う。

| 対象 | 判断 |
|:-----|:-----|
| **plain class のロジック**（層を問わない） | **対象。** メソッド呼び出しで観測できるので EditMode で検証する |
| **MonoBehaviour / `*LifetimeScope` 継承クラス** | **スキップ。** ランタイム挙動はユーザー手動確認へ委譲（`rules/testing.md`） |
| **UXML / シーン / prefab に依存する表示反映・入力配線** | **スキップ。** 同上 |

- `Presentation/` は層としては除外しない。**Model / Manager / Provider 等の plain class は対象**（種別名で判定するのではなく、plain class かどうかで判定する。`rules/class-catalog.md` は非網羅の対応表）
- **View / Binder は MonoBehaviour または UXML 部分木に依存するのでスキップ**
- **Presenter は原則スキップ**（View 具象に依存するため単体テストの境界が引けない）。Presenter に配線以上のロジック（表示判定・値域制約・状態遷移）が入っているなら、テストをこじ開けるのではなく **Model へ切り出す**（§9・`rules/class-catalog.md`）
- Domain / Application / Infrastructure に MonoBehaviour は存在しない（`rules/architecture.md`）ので、これらは常に対象

## 2. このプロジェクトのテスト層

本プロジェクトの自動テストは **EditMode の単体 / ロジックテストに限定**する。

- 検証するのは「**メソッドの直接呼び出しで起動する振る舞い**」（純ロジック、State 遷移、エラー変換等）。
- PlayMode / 統合テスト / 視覚検証 / 画像解析は**自動スイートでは扱わない**。MonoBehaviour・UXML・シーンに依存するランタイム挙動・見た目・マルチプレイヤー挙動は**ユーザー手動確認**に委譲する（`rules/testing.md`「ランタイム動作確認フロー」）。
- したがって設計対象は常に「unit / logic test」であり、層を PlayMode へ分割しない。

## 3. テスト技法の選択

### spec-based > structural（最重要原則）
**仕様ベース（観測可能な振る舞いを検証）を、構造ベース（実装の内部分岐をなぞる）より優先する。**
構造テストはリファクタで壊れ、価値が急速に失われる。実装に不安があるとき一時的に構造テストを書くのは可だが、**仕様テストが同じ振る舞いを覆ったら削除する**。private 実装詳細に依存したテストは原則作らない。

### 技法
| 技法 | 使う場面 |
|:-----|:---------|
| 同値分割 | 入力を valid / invalid に分け、各区分の代表 1 件 |
| 境界値分析 | 各区分の境目。過剰にやらずパラメータ化で集約。仕様が境界で挙動を変えないなら代表 1 件で可 |
| 状態遷移 | FSM を持つ対象。1 ケース = 0-switch（A→B の直接遷移）|
| デシジョンテーブル | 複数条件の組合せで結果が変わる場合 |
| エラー推測 | 経験則。キャンセル中の操作、二重呼び出し、数値オーバーフロー、ネットワーク失敗等 |

### 無効同値（invalid partition）の扱い
- **UI から入りうる無効入力**（数値フィールドの範囲外等）= システム境界の実在する失敗経路 → テストする。
- **仕様が挙動を定義していない無効入力**（負値・null 等で何が起きるべきか不明）→ **推測して期待値を作らない**。`AskUserQuestion` で確認してから設計する。確認できない場合は「未定義仕様」として報告し、そのケースは書かない（現行実装の挙動を読んで期待値にすると、実装のスナップショットを固定するだけになる）。

## 4. 依存のエラー経路をテストするか（外部 vs 自前）

依存の失敗パスを検証すべきかは、その依存の出自で決める:

| 依存の出自 | 判断 |
|:-----------|:-----|
| **外部ライブラリ / framework / SDK**（本プロジェクトの所有外。例: 音声/ネットワーク SDK・HTTP backend） | **テストする。** stub でエラー条件を注入し、エラー変換・ガード・状態整合を検証する |
| **自前コード**（本プロジェクトの別コンポーネント） | **skip。** 内部コードの正しさは信頼し、その依存の単体テスト側で守る |
| **不明** | `AskUserQuestion` で確認してから設計する。確認できない場合はテストせず報告する |

> 例: 外部 SDK の未接続時に `NotConnected` へ変換するガードは「外部依存のエラー変換」なので **valuable**。一方、自前の下位 UseCase が返す失敗を上位でもう一度確認するだけのテストは「自前コードの再検証」なので不要（§6 も参照）。

**エラー変換の検証は「変換の方針」に絞る**（未知コードが既定値へ落ちる / 情報を落とさない / 変換後も状態が整合する）。
代表 2〜3 件で足りる。エラー enum を全要素列挙して 1 対 1 の対応表を第 2 の場所に書き写さない
（対応表の写経は、表を間違えたまま両方直せば黙って通るので回帰を殺さない）。
context 境界をまたぐ内部 enum の再マッピングは、外部由来の入力を注入する経路ではないのでテストしない。

## 5. テスト価値の判定（追加前ゲート）

追加候補ごとに、**すべて**満たすか確認する。1 つでも満たせないものは追加しない。

### ゲート 1: 回帰特定（反証可能な形で述べる）
そのテストが**落ちる具体的な実装改変を 1 つ挙げられる**こと（どのメソッドのどの条件式・どの代入をどう変えると落ちるか）。
挙げられないなら追加しない。

「仕様を守るテストです」「正しく動くことを確認します」は説明ではない。**改変を名指しできるかどうか**で判定する。

### ゲート 2: 一意性（反冗長）
**重複** = 別テストと**同じ実装箇所の同じ回帰**を殺している。ゲート 1 で挙げた改変が既存テストも落とすなら、
condition や assertion の字面が違っても重複であり追加しない。

- **同一のガード実装を、公開 API の数だけ反復しない。** 残すのは最も上位の入口 1 件（例: Room 送信と DM 送信が同じ未接続ガードを通るなら 1 件）。入口ごとに**別の**実装箇所を通る場合のみ複数書く
- 入力値だけが違う再確認はパラメータ化で 1 メソッドに集約する（§7）
- **同一 condition のテストを multi-assert に統合しない**（1 ケース 1 検証）。ただし次の 2 つは 1 メソッドにまとめて assert する:
  - 状態遷移後に複数プロパティが同時に正しくある必要がある場合
  - 外部購読される状態の初期契約（§8）— プロパティごとにテストを分けない

### ゲート 3: 仕様語 ↔ assertion 整合（反 fake）— 観測可能性
テストの意図・コメントに**仕様語**（順序 / rollback / fallback / エラー変換 / 状態遷移 / キャンセル伝播）が出るなら、それを**実際に観測する assertion** が存在すること。

**検証は「観測可能な性質」だけを述べる。** 以下を検証内容に混ぜない（= fake の温床）:
- なぜこのテストが存在するか / 現在のバグ挙動（rationale）
- テスト機構（属性・sync/async・assertion の形）
- 入力の構築手順

| | 例 | 問題 |
|:--|:--|:--|
| ❌ Bad（rationale 漏れ） | 「同一シードで再現する。RNG が holder に格納されない現状では失敗する（BUG再現）」 | なぜ存在するかを書いている。観測内容のみにする |
| ✅ Good | 「同一シードで 2 回実行するとマップ構造が一致する」 | 観測可能な振る舞いのみ |
| ❌ Bad（順序を主張するが観測しない） | コメント「leave→logout の順序を守る」だが assert は state クリアのみ | 順序を観測していない fake |
| ✅ Good | 呼び出し順を記録し `IndexOf(leave) < IndexOf(logout)` を assert | 仕様語を実観測 |

### ゲート 4: テストダブルの語彙（xUTP）
| ダブル | 役割 | 検証での扱い |
|:-------|:-----|:-------------|
| **Stub** | 定型レスポンスを返し SUT を隔離 | arrange の関心事。検証意図に書かない |
| **Spy** | 呼び出し・引数を記録し後で検証 | **検証対象**。順序・呼び出し回数を観測するなら spy を使う |
| **Fake** | 簡易だが動作する実装 | arrange の関心事。検証意図に書かない |

不要なダブルを増やさない。検証したいのが「呼ばれたか・順序」なら spy、「SUT を動かすため」なら stub/fake。

## 6. 複数コンポーネントを束ねるクラスのテスト方針

下位を合成するクラス（Orchestrator 等）のテストは、**下位が単体テストで既に保証している結果 state を再検証しない**（例: `CurrentUserState` クリア）。合成側に固有の契約のみを観測する:

- **呼び出し順序** → 呼び出し順記録（spy / order recorder）で観測
- **継続条件**（下位失敗時に後続を best-effort で続行する 等）
- **キャンセル伝播**（OCE を握りつぶさず後続を実行しない 等）

ただし**順序テストを書くのは、順序が入れ替わったときに観測可能な障害が起きる場合に限る**
（サーバーが拒否する / 二重課金になる / 後続が未初期化状態を読む 等）。
「実装がその順に書かれているから」を理由に順序を固定するテストは、実装文面の転写なのでリファクタで必ず壊れる。

下位の成果 state を上位で再確認するだけのテストは「実装をなぞるだけ」に該当し追加しない。

## 7. 重複検出と統合（書いた後の dedup パス）

テストを書いた後、追加・変更したファイル + 同一テストクラスの既存テストを読み、§5 ゲート 2 の定義で重複を検出する。

- **重複**（同じ実装箇所の同じ回帰を殺している）→ より正確な名前のものを残し、他を削除。
- **パラメータ化マージ**: condition が違っても「SUT に渡す引数だけが違い、**同一同値区分**で**同一の期待結果**」なら、パラメータ化テストに統合する。
  - パラメータ化テスト本体に `if` / `switch` を書かない
  - **期待値をパラメータ化しない**（期待値が分岐するなら別区分 = 別テスト）
  - 異なる同値区分・異なる期待結果のケースは統合しない
- **禁止リスト該当の既存テスト**（`rules/testing.md`「禁止する低品質テスト」）を見つけたら削除を提案する。
  追加時フィルタだけでは既存分が残り続け、しかも「既存テストで十分」判定の材料に化ける。

## 8. 追加禁止の低品質テスト

追加してはならない低品質テストの一覧は `rules/testing.md`「禁止する低品質テスト」を単一ソースとする
（fake assertion・合成側での結果 state 再検証などを含む）。ここでは重複させない。

**初期値テストの例外**: **外部から購読される状態の初期契約**を守る場合に限り許容する
（購読側が初期値に依存して表示・分岐を決める、という意味での契約。単に「フィールドの初期化子を読み返す」テストは対象外）。
許容する場合も**プロパティごとにテストを分けず、1 メソッドにまとめて assert する**（§5 ゲート 2 の例外）。

## 9. テスタビリティの評価

設計中に「テストが書きにくい」と感じたら、それは**テストの問題ではなく対象コードの設計問題**の兆候。
無理にテストをこじ開けず、以下のいずれかなら設計見直しを報告する（`rules/coding-standards.md`「根本設計から作り直す」に従う）:

- 単体テストの境界が引けない（SUT が大きすぎる）
- 状態が隠蔽され外部から観測できない
- 条件数に対しテストケースが O(n) より速く増える（組合せ爆発）
- 依存が注入できない（static / global 結合、constructor 内 `new`）
- **MonoBehaviour（View / Presenter 等）に純ロジックが埋まっていて分離されていない** → Model または純関数へ切り出す

この場合、テストを書く前に対象の分割・依存注入化・状態公開を提案する。
